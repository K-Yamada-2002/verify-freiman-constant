# 有限の帰納証明が存在すれば発見する探索

2026-09-23。

## 1. 保証する命題

対象は従来どおり、`P=313121`、
`A_n=(3211P^n3 | 4322P^n)`、全 `n>=0` の凸包全体。
新しく追加する数字は `{1,2,3}`、禁止語は `31313`。

今回の探索には次の**相対的完全性**がある。

> 現在の `PiecewiseVerifier.closed()` が受理する有限の証明書が存在すれば、
> 計算を上限なく継続することで、そのような証明書を有限時間に発見する。

有限時間で実行を打ち切った時点での成功、実用的な計算時間、または
充填命題が真なら必ずこの形式の有限証明が存在することは保証しない。
新たな数学的表現が必要な証明は、現形式に対するこの定理の範囲外である。
この保証では、必要な記憶容量も利用できることを仮定する。
実機で資源不足が続く場合はその候補で止まり、候補を誤って捨てることはしない。
現時点で全帰納の閉鎖は確認していない。

## 2. 有限候補の中では決定手続きになる

型集合を \(T\)、型 \(t\) の規則集合を \(R(t)\)、規則 \(r\) の子を \(C(r)\) とする。

\[
X_0=T,\qquad
X_{k+1}=\{t\in X_k:\exists r\in R(t),\ C(r)\subseteq X_k\}.
\]

有限集合からの減少列なので停止する。最後の集合は最大の閉じた部分系である。
閉じた帰納系 \(S\) があれば、\(S\subseteq X_k\) が全段階で保たれ、誤って削除されない。
逆に最後まで残った各型には、その集合内に子を持つ規則がある。
それらを選ぶと有限の閉じたグラフになる。

実装は、現在選んでいる規則の子が削除されたとき、その親で**全候補を再検索**する。
一つ目の規則が失敗しても、別の規則による相互帰納を残す。
選択した規則の逆参照を使い、影響を受けた親だけを処理し直す。

### 今回の有限候補集合を正確に定める

保存済みグラフを読み、同じ領域と同じ厳密な両端点の型を統合する。
有限候補内で認める規則は次の全体である。

1. **全く同じパラメータ領域**で保存されている子の提示区間を使用する。
2. それらを任意の順序でつなぎ、目標全体を覆う全ての鎖を認める。
3. 各提示区間に保存されている到着先は、任意の部分集合を使用できる。
4. 同じ親領域に保存されている場合分けを全て認め、各領域で1〜3を行う。
5. 初期型は、各入力で厳密に確認済みの初期型から選べる。

新しい語・領域・場合分けを追加することは、この**有限候補の判定**には含めない。
それらを固定せず探索するのは、後述する独立した全列挙の役割である。

### 被覆の候補を絞っても完全性を失わない箇所

規則全体を明示的に全列挙すると巨大になるため、有限個の端点の到達可能性として判定する。
現在の右端 \(p\) から提示区間 \([a,b]\) へ進む条件は、領域全体で
\(a\le p<b\)。この条件を厳密に検査し、到達した右端を全て探索する。
同じ右端に着けば以降の可能性は同じなので、同じ右端の再探索だけを省く。
候補数32などの上限や、浮動小数による接触の棄却は使わない。

到着先の部分集合も明示的に全列挙する必要はない。
保存辺の到着先は、個々の向きと提示区間の包含がすでに検証されている。
現在残っている到着先を全て集めて全像を覆えなければ、その部分集合でも覆えない。
全て集めれば覆える場合は、それ自身が一つの許容される選択となる。
共通座標系ごとの全像被覆は、従来の厳密検証器で判定する。

### 有限候補での否定結果も再検査する

削除順を保存し、初めの全集合から順に再実行する。
各削除時点で、残る型だけを使った規則がないことを再確認する。
最後の生存集合についても、内部で成立する規則を全件確認する。
これにより「今回の有限候補集合では閉じない」と「探索途中」を区別する。

## 3. 型数や語長を固定しない全列挙

`complete_certificate_codec.py` は証明書を有限ビット列で表す。
自然数、符号付き整数、有理数、\(\mathbb Q(\sqrt{462})\) の係数、語、端点、
領域、子の参照、場合分けを有限の文法で符号化する。
端点の有理内挿 `word@weight` も扱う。
型数・語長・係数の大きさ・場合分け数に固定上限は設けない。

列挙番号 \(m=0,1,2,\ldots\) に対し、\(m+1\) の2進表記から先頭の1を除く。
列挙されるビット列は

```text
空列, 0, 1, 00, 01, 10, 11, 000, ...
```

となる。全ての有限ビット列が、有限の番号で一度ずつ現れる。
各候補は文法に従って読み、構文が正しければ `PiecewiseVerifier.closed()` で検査する。
証明書は実行可能なプログラムではなく、有限のデータである。
構文解析は入力のビットを消費して進み、検証器も有限の型・辺・箱の境界を処理するため、
各候補の検査は有限回の厳密演算で終わる。

**存在すれば発見することの証明。**
受理される有限証明書が一つあると仮定する。不要な節点を除き、係数などを標準表記にすれば、
実装した符号化器で有限ビット列になる。その列の番号を \(M\) とする。
\(M\) より前の候補は有限個で、各検査は有限時間で終わる。
従って番号 \(M\) の検査まで有限時間で到達し、証明書を受理する。

これは使用する厳密演算と検証器が正しいという前提でのアルゴリズムの証明であり、
試験例が成功したことだけから完全性を推測しているわけではない。

## 4. 公平な実行と再開

`search_complete_induction.py` は1巡につき

1. 全列挙を既定256候補進める。
2. 有限候補の閉鎖判定を1件進める。

を繰り返す。有限候補の判定が終わった後も全列挙を続ける。
有限候補の一つの問い合わせは有限時間で終わるため、全列挙が永久に後回しにならない。

列挙位置、完了した候補数、削除済みの型、待ち行列、選択済み規則を保存する。
時間上限は実行一回の上限であり、再開時に列挙位置を0へ戻さない。
上限の確認は有限の処理単位の間で行うため、一件が重いと指定秒数を超えることがある。
ライブラリの構築と入力監査の時間は探索の秒数上限に含めない。

構文不正・厳密検証による拒否と、メモリ不足などの実行上の失敗を区別する。
後者では候補を棄却せず、列挙位置を進めない。
検証器・列挙器・候補ライブラリのハッシュが異なる状態からの継続は拒否する。
有限候補の判定が不成立でも、全体について「証明なし」とは記録しない。

## 5. 実用上の位置付け

全ビット列の列挙は非常に遅く、これだけで短時間の発見を期待できない。
長さ \(B\) の証明書には、おおむね \(2^B\) 個規模の先行候補がある。
実際の探索速度を担うのは、保存規則をまとめて扱う有限候補の閉鎖判定である。
今後、候補の自動生成を改善しても、全列挙へ計算時間を確保し続ければ、この保証を保持できる。

従って今回の変更は、帰納の存在を新たに証明したことを意味しない。
「現形式の有限証明があるのに、固定上限やヒューリスティックのため永久に探索対象に入らない」
という問題を解消する。

## 6. 実行方法

```sh
cd Freiman/schecker_generalized
python3 search_complete_induction.py \
  frontier_reduced_eleven.json frontier_final.json \
  frontier_recipe_eight.json frontier_policy_eight.json \
  --seconds 180 --output complete_induction_run.json

python3 search_complete_induction.py \
  --resume complete_induction_run.state.json \
  --seconds 180 --output complete_induction_run.json
```

単一の実行の時間上限も外す場合は `--seconds inf` とし、`--epochs` は指定しない。
通常は有限時間ごとに保存し、同じ状態から継続することで列挙の進行を保持できる。

成功時のみ `.certificate.json` と `.verified.json` を出力し、最後に新しい検証器で
全帰納を再検証する。未完了時は状態と結果報告だけを保存する。

試験:

```sh
python3 -m unittest test_complete_induction test_piecewise_charts \
  test_frontier_reduction test_rule_reuse
```

29試験が通過した。このうち今回追加した12試験には次が含まれる。

- 80個の小さなランダムなAND/OR系を全ての部分集合の検査と比較する。
- 最初に選んだ規則が失敗した後、別の規則による相互帰納を発見する。
- 状態を保存・復元しても、判定結果と列挙する候補順が一致する。
- 資源不足で候補番号が進まず、処理途中の中断で型が抜け落ちない。
- 実際の条件付き証明書を符号化・復号し、厳密監査を通す。
- 途中の比較で右端の大小が交差する場合も、必要な被覆鎖を発見する。
- 実際の有限候補について、削除順を再検証する。
- 規則の重複除去が、ハッシュ値の衝突がないという仮定に依存しない。

従って、**第2節で定めた有限候補集合では、初期目標の帰納は閉じない**。
一つの選択済みグラフが閉じないという結果から進み、保存された提示区間の
任意の鎖・到着先の任意の部分集合・保存された場合分けを含めて否定した。
新しい提示区間や別の領域などを使う帰納の不存在は主張しない。

最終版は保存済み候補ライブラリから8,000巡、探索時間約135.81秒実行した。
その後、実際の保存状態を復元し32巡追加した。
全列挙の番号は2,048,000から2,056,192へ進み、その8,192候補の独立再実行と結果が一致した。
有限候補側の状態も完全に一致していた。

全列挙で処理した2,056,192ビット列のうち、2,054,324件は構文不正、
構文が通った1,868件は厳密検証で拒否、受理は0件。
ここまでの記述は最大20ビットであり、これを大量の有望な帰納戦略を調べた件数とは解釈しない。
全列挙の実用上の遅さは残っている。

別途、現行の2,848型の部分戦略を3,995,962ビットに符号化し、復号・再符号化と
列挙番号との往復を確認した。証明書の全構造のハッシュは元と完全に一致した。
この部分戦略そのものは未解決義務を含む。
